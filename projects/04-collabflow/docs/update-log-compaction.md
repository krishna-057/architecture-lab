# CollabFlow Durable Update Log And Compaction Notes

CollabFlow should persist Yjs update history only after the websocket provider lifecycle is proven. The durable log is a recovery and replay mechanism for document updates; it is not a replacement for Yjs merge semantics and it must not include awareness presence.

## Proposed Tables

The next durable-sync slice should add two tables beside the existing snapshot tables:

```sql
create table collabflow_yjs_updates (
  update_id bigserial primary key,
  workspace_id uuid not null references collabflow_workspaces(workspace_id) on delete cascade,
  update_seq bigint not null,
  update_bytes bytea not null,
  update_hash text not null,
  client_id text not null,
  created_at timestamptz not null,
  compacted_at timestamptz,
  unique (workspace_id, update_seq),
  unique (workspace_id, update_hash)
);

create table collabflow_compaction_checkpoints (
  checkpoint_id uuid primary key,
  workspace_id uuid not null references collabflow_workspaces(workspace_id) on delete cascade,
  compacted_through_seq bigint not null,
  state_vector bytea not null,
  snapshot_update bytea not null,
  created_at timestamptz not null
);
```

`update_seq` gives each workspace a monotonic replay order. `update_hash` makes duplicate websocket retries idempotent. `snapshot_update` stores a compact Yjs state update generated by applying the earlier updates to a server-side Yjs document in a worker or maintenance job.

## Replay Rule

On `sync_request`, the server should send:

1. The newest compaction checkpoint for the workspace, if one exists.
2. All non-compacted updates where `update_seq > compacted_through_seq`.
3. A `sync_ready` response that includes `checkpoint_id`, `compacted_through_seq`, and the replayed update count.

Clients still load IndexedDB first, then apply server replay. Yjs handles duplicate or overlapping updates, but the server should still keep replay order stable so reconnect behavior is easy to reason about.

## Compaction Triggers

The first production-friendly policy should be simple:

- Compact after 500 un-compacted updates for a workspace.
- Compact when the un-compacted update bytes exceed 2 MiB.
- Compact opportunistically after a durable snapshot export.
- Keep at least the latest checkpoint plus its tail updates.

Compaction can run inline for local development, but production should move it to a background worker so websocket fanout is not blocked by large document merges.

## Retention Rule

After a checkpoint is written and verified, older updates can be marked with `compacted_at` instead of deleted immediately. A later cleanup job can delete compacted rows after a short retention window. Keeping a window makes failed deploys and broken compaction code easier to roll back.

Awareness messages must never enter this log. They are connection state, not document history.

## Failure Modes

- If compaction fails, keep replaying the uncompacted log and report the error; do not drop updates.
- If a duplicate update arrives, return the existing sequence instead of appending a new row.
- If checkpoint replay fails on a client, the client should request a full replay tail or fall back to its IndexedDB projection plus later updates.
- If PostgreSQL is unavailable, the server should refuse durable-sync mode rather than silently pretending in-memory replay is durable.

## Deferred Implementation

This note intentionally stops before adding durable websocket update writes. The current API still uses an in-memory `sync_update_log`; exported snapshots are already durable through PostgreSQL when configured. The next implementation slice should add the update tables, append-only websocket persistence, replay from PostgreSQL, and a small compaction smoke test.
